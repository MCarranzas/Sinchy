 AVISO LEGAL / OPERATIVO
 -----------------------
 Este sistema calcula y registra liquidaciones de mineral: son datos con valor
 economico y fiscal. Un plan gratuito tiene reinicios, suspensiones por
 inactividad, sin disco persistente y sin respaldo administrado. Sirve para
 demostrar el sistema, para un piloto o para una capacitacion. Para operar de
 verdad con liquidaciones reales, la recomendacion tecnica de este documento es
 la OPCION A (una maquina virtual "siempre gratis"), que es la unica que
 reproduce completa la arquitectura que el propio sistema espera (Nginx +
 PHP-FPM + PostgreSQL + cron + disco).

================================================================================
 0. RESUMEN EJECUTIVO
================================================================================

 El sistema son DOS aplicaciones, no una:

   1) epcoro-api/  -> API REST en Laravel 13 (PHP 8.4) sobre PostgreSQL 17.
   2) epcoro-web/  -> interfaz de usuario (SPA) en Vue 3 + Vite 8 + Tailwind 4.

 La SPA NO tiene datos ni logica de negocio propia: consume la API en /api/v1.
 La autenticacion es por COOKIE DE SESION (Laravel Sanctum modo SPA), no por
 token. Esto tiene una consecuencia que manda sobre toda la estrategia de
 despliegue:

       LA SPA Y LA API DEBEN VIVIR EN EL MISMO DOMINIO (mismo origen).

 Si se despliegan en dominios distintos (por ejemplo SPA en Netlify y API en
 otro host), el navegador trata la cookie de sesion como cookie de terceros y
 la bloquea: el login "funciona" pero la sesion se pierde en la peticion
 siguiente. Ademas el cliente HTTP del frontend tiene la ruta fija '/api/v1'
 (ver epcoro-web/src/api/axios.ts), asi que no hay forma de apuntarlo a otro
 dominio sin modificar codigo.

 De ahi que toda opcion viable sea "un solo origen": un servidor que sirva los
 archivos estaticos de la SPA y, en el mismo dominio, enrute /api y /sanctum
 hacia Laravel.

 Lo que el sistema NO necesita (esto abarata mucho el despliegue):
   - NO usa Redis ni Memcached: cache, sesiones y cola van en la base de datos.
   - NO usa colas en segundo plano: no hay ningun Job/ShouldQueue en el codigo.
     La generacion de PDF y Excel es sincrona.
   - NO usa S3 ni almacenamiento de objetos: no hay carga de archivos.
   - NO usa servidor de correo: MAIL_MAILER=log (no manda correos).
   - NO usa WebSockets ni notificaciones en vivo.
   - NO usa Docker obligatoriamente: es PHP + PostgreSQL, se instala directo.

 Con todo eso, los requisitos reales de un plan gratuito son solamente:
   PHP 8.4 con extensiones, PostgreSQL, unos 200 MB de disco, HTTPS y (opcional
   pero recomendado) una tarea cron diaria. Eso descarta de entrada a los
   hostings gratuitos tipo MySQL/InfinityFree (no tienen PostgreSQL) y a los
   hostings puramente estaticos (no ejecutan PHP).

 Recomendacion corta:
   - Sin tarjeta, para demo/piloto ......... OPCION C (Alwaysdata Free)
   - Sin tarjeta, para demo "de vitrina" ... OPCION B (Render Free + Neon Free)
   - Para uso real ......................... OPCION A (VM "siempre gratis")

   Extensiones necesarias EN LA PRACTICA y que Composer NO declara (porque no

     ext-bcmath    -> OBLIGATORIA. El calculo de la liquidacion
                      (app/Services/CalculoLiquidacionService.php) usa bcmul,
                      bccomp, bcadd, bcsub. Sin bcmath el sistema instalado con

                      ESTA ES LA TRAMPA MAS FACIL DE PISAR EN UN SERVIDOR NUEVO.
     pdo_pgsql     -> obligatoria (conexion a PostgreSQL).
     pgsql         -> recomendada (cliente PostgreSQL).
     curl          -> recomendada (Guzzle/HTTP saliente).
     intl          -> opcional (formato de numeros/fechas es_BO).
     opcache       -> muy recomendada (rendimiento).
     fileinfo      -> viene con ext-fileinfo (ya listada arriba).

   En Debian/Ubuntu, el paquete que las instala todas de una vez es, por
   ejemplo:

     apt install -y php8.4-cli php8.4-fpm php8.4-pgsql php8.4-mbstring \
       php8.4-xml php8.4-gd php8.4-zip php8.4-bcmath php8.4-curl \
       php8.4-intl php8.4-opcache php8.4-common

   (php8.4-xml arrastra dom, libxml, simplexml, xmlreader y xmlwriter.)

 3. ARQUITECTURA DE PRODUCCION QUE EL SISTEMA ESPERA
================================================================================

 3.1 DIAGRAMA (UN SOLO DOMINIO)

                         https://liquidaciones.dominio.gob.bo
                                     |
                                     v
                     +-----------------------------------+
                     |            NGINX  (443/TLS)       |
                     |                                   |
                     |  /                -> dist/ SPA    |
                     |  /api/*           -> PHP-FPM      |
                     |  /sanctum/*       -> PHP-FPM      |
                     |  /up              -> PHP-FPM      |
                     +----------------+------------------+
                                      |  fastcgi (9000)
                                      v
                     +-----------------------------------+
                     |      PHP-FPM  (Laravel 13)        |
                     |      epcoro-api/public/index.php  |
                     +----------------+------------------+
                                      |  pgsql (5432)
                                      v
                     +-----------------------------------+
                     |        PostgreSQL 17              |
                     +-----------------------------------+

   La SPA (archivos estaticos con hash en el nombre, cacheables por 30 dias) y
   la API comparten dominio, puerto y certificado. Nada de CORS en la practica
   (el navegador lo ve como mismo origen) y la cookie de sesion viaja sin
   problemas.

 3.2 REGLA DEL MISMO ORIGEN (por que no se puede separar)

   1) La sesion es una COOKIE. Con SPA en dominio A y API en dominio B, la
      cookie es "de terceros". Safari la bloquea por defecto; Chrome la bloquea
      en modo incognito y la limita en navegacion normal. El sintoma tipico es
      "entro y al hacer clic me devuelve al login".
   2) El cliente axios tiene baseURL '/api/v1' (relativa). Apuntarlo a otro
      dominio exige editar codigo y reconstruir el frontend.
   3) `supports_credentials = true` con origen cruzado obliga a SameSite=None
      mas Secure, y aun asi el navegador puede descartar la cookie.

   Conclusion: aunque tecnicamente se pueda "proxear" /api desde un CDN
   (Cloudflare Pages con _redirects, Vercel con rewrites), eso agrega una capa
   fragil para ahorrar un servidor. No vale la pena.

 3.3 AJUSTES NECESARIOS PARA SERVIR LA SPA DESDE NGINX

   a) Fallback de historial: cualquier ruta que no sea un archivo real debe
      devolver index.html, si no, recargar https://dominio/bandeja da 404.
      Se resuelve con `try_files $uri $uri/ /index.html;` (Anexo C).

   b) Rutas de la API antes que el fallback: `location ~ ^/(api|sanctum)/`
      debe resolverse a Laravel, nunca a index.html.

   c) Cache: los archivos de dist/assets llevan hash en el nombre, se pueden
      cachear de forma agresiva. index.html NO se cachea.

   d) Tema del 404 de la API: la API responde JSON con 404; el fallback de la
      SPA no debe interceptar /api (por eso el punto b va primero).

   El archivo REAL que implementa esto es `docker/nginx.conf.template`
   (Anexo C). El puerto se inyecta con `envsubst` en el arranque porque el
   proveedor lo entrega en la variable PORT.

 5. SECUENCIA DE DESPLIEGUE (GUION GENERAL)
================================================================================

 Sirve para cualquier opcion de la seccion 6. Los nombres de carpeta son los
 que usa este documento: /var/www/api (Laravel) y /var/www/web (SPA construida).

 --- FRONTEND (se construye aparte; puede hacerse en tu PC) -----------------

   cd epcoro-web
   npm ci                     # instalacion reproducible desde package-lock
   npm run build              # vue-tsc -b && vite build  ->  dist/
   # subir SOLO la carpeta dist/ al servidor, por ejemplo a /var/www/web

 --- BACKEND -----------------------------------------------------------------

   cd /var/www/api
   composer install --no-dev --optimize-autoloader --no-interaction

   cp .env.production.example .env     # y completar valores reales
   php artisan key:generate            # genera APP_KEY (solo la primera vez)

   php artisan migrate --force         # --force porque APP_ENV=production
   # Datos base (ver Anexo F): NO correr `db:seed` a secas en produccion.

   php artisan config:cache
   php artisan route:cache
   php artisan view:cache

   php artisan sinchiwayra:revisar-produccion    # debe terminar en 0
   php artisan optimize                        # alias de lo anterior en Laravel 13

   # Permisos de escritura (Laravel necesita escribir en storage y cache):
   chown -R www-data:www-data storage bootstrap/cache
   chmod -R ug+rwX storage bootstrap/cache

   # Tarea programada (cron del usuario del servicio):
   * * * * * cd /var/www/api && php artisan schedule:run >> /dev/null 2>&1

 Notas del guion:
   - `config:cache` es OBLIGATORIO en produccion: sin el, cada peticion lee el
     .env. Si despues se cambia una variable de entorno hay que volver a
     ejecutar `php artisan config:cache`.
   - `route:cache` SE VERIFICO el 15/10/2026 con Laravel 13 y funciona incluso
     con la ruta con closure de routes/web.php ("Routes cached successfully").
   - Despues de desplegar codigo nuevo: `php artisan config:cache && php artisan
     route:cache && php artisan view:cache` (o `php artisan optimize`).
   - NUNCA subir: .env, vendor/ (se instala), node_modules/, dist/ del repo,
     y MUCHO MENOS usuarios_prueba.txt (contiene credenciales de prueba).
   - Este guion manual aplica a la Opcion A (servidor propio). Para la imagen
     Docker (Anexo B; Opciones B/C y Railway) los pasos de FRONTEND y BACKEND
     los hace la propia imagen: el build compila la SPA y `docker/start.sh`
     aplica migraciones y cachea la configuracion al arrancar.

 6.1 FILTROS (lo que descarta una opcion de entrada)

   R1. Debe ejecutar PHP 8.4 con las extensiones de la seccion 2.
   R2. Debe ofrecer PostgreSQL (no MySQL, no solo SQLite).
   R3. Debe permitir servir estaticos Y PHP en el MISMO dominio (seccion 3.2).
   R4. Debe tener HTTPS con certificado valido.
   R5. Debe tener ~200 MB de disco (vendor + codigo + dist; con --no-dev ~70 MB).
   Deseables:
   D1. Disco persistente (para logs de auditoria de 180 dias y respaldos).
   D2. Una tarea cron (para el respaldo diario).
   D3. Dominio propio (para que la URL sea institucional y no un subdominio
       ajeno). Sin esto, la direccion cambia si se muda de proveedor.

 6.2 OPCION A - MAQUINA VIRTUAL "SIEMPRE GRATIS"  (RECOMENDADA PARA USO REAL)

   Proveedores:
     - Oracle Cloud "Always Free": VM Ampere ARM. ATENCION: en julio de 2026
       Oracle redujo la asignacion gratuita de Ampere (las fuentes reportan del
       orden de 2 OCPU / 12 GB en lugar de 4/24; verificar el cupo vigente al
       crear la cuenta). Requiere tarjeta de credito para el registro.
     - Google Cloud "Always Free": una VM e2-micro (1 vCPU / 1 GB) en
       us-central1, us-west1 o us-east1, con 30 GB de disco. Requiere tarjeta.
     - (AWS, Azure y otros: sus capas gratuitas son por 12 meses, no permanentes.)

   Por que es la recomendada: es la unica que cumple D1, D2 y D3, y la unica que
   reproduce exactamente la arquitectura del README (Nginx + PHP-FPM +
   PostgreSQL). La maquina nunca se apaga, no hay arranque en frio y el respaldo
   corre de verdad.

   Montaje:
     a) Instalar Ubuntu LTS (o el sistema que ofrezca el proveedor).
     b) Instalar PHP 8.4 + extensiones (seccion 2.1), Nginx, PostgreSQL 17,
        Composer, cron y pg_dump. Alternativa: Docker Compose (Anexo D).
     c) Crear la base y el usuario:
          sudo -u postgres createuser --pwprompt epcoro
          sudo -u postgres createdb --owner=epcoro epcoro
     d) Desplegar con el guion de la seccion 5 y la config de Nginx del Anexo C.
     e) HTTPS: usar Caddy (certificado automatico, 3 lineas) o
        `certbot --nginx`. Con Cloudflare por delante tambien se puede usar su
        certificado de origen.
     f) Cron del respaldo (seccion 5) y cron de renovacion del certificado si
        se uso certbot.
     g) Cortafuegos: abrir SOLO 80 y 443 al mundo; 5432 (PostgreSQL) nunca
        expuesto a Internet; SSH por llave, no por contrasena.

   Contras: exige manejar un servidor (parches, copias, certificados). No hay
   boton magico.

 6.3 OPCION B - RENDER (FREE, DOCKER) + NEON (POSTGRES FREE)  (DEMO, SIN TARJETA)

   Verificado el 15/10/2026 contra la documentacion oficial de Render
   (render.com/docs/free):

     Plan Free de Render, servicio web (Docker):
       - 750 horas de instancia al mes. Si se agotan, Render SUSPENDE los
         servicios gratuitos hasta el mes siguiente.
       - Se APAGA a los 15 minutos sin trafico y tarda ~1 minuto en despertar.
       - Sistema de archivos EFIMERO: lo que se escriba en disco se pierde en
         cada reinicio, redespliegue o apagado.
       - 0,1 CPU / 512 MB de RAM. Sin disco persistente. Sin acceso SSH.
       - Sin trabajos "one-off" y sin escalado.
       - Bloquea los puertos SMTP (25, 465, 587) de salida.
       - Dominio propio y HTTPS: SI, incluidos y gratuitos.
       - La propia documentacion de Render advierte: "Do not use them for
         production applications."
     Plan Free de Render, PostgreSQL:
       - 1 GB de almacenamiento y, sobre todo, EXPIRA A LOS 30 DIAS de creada
         (14 dias de gracia y luego se BORRA con todos los datos).
       - Una sola base gratuita por cuenta y sin respaldos administrados.
       => NO usar la base gratuita de Render para esto. Usar una base externa.

     Neo (Neon.tech) plan Free (PostgreSQL gestionado):
       - Almacenamiento del orden de 0,5-1 GB por proyecto y ~100 horas de
         computo al mes (las cifras cambiaron varias veces durante 2026: leer
         la pagina de precios vigente).
       - Escala a cero cuando no hay actividad: la primera consulta del dia
         puede tardar unos segundos (se suma al minuto de despertar de Render).
       - Permite restaurar a un punto en el pasado dentro de su ventana de
         retencion (limitada en el plan gratuito).
       - Conexion por SSL obligatoria => DB_SSLMODE=require.

   Montaje resumido:
     1) Crear la base en Neon y copiar su cadena de conexion.
     2) Crear en Render un "Web Service" desde el repositorio de GitHub y
        apuntarlo al Dockerfile de la RAIZ del repositorio (Anexo B, ya
        implementado). El "Root Directory" debe quedar en la raiz del repo.
        Render construye la imagen e inyecta la variable PORT (por defecto
        10000); Nginx escucha en ella via envsubst (docker/start.sh).
     3) Cargar las variables de entorno de la seccion 4 en el panel de Render
        (incluyendo DB_* de Neon, DB_SSLMODE=require y APP_KEY).
     4) Primer despliegue: ejecutar las migraciones. Como no hay SSH, se hace
        desde el arranque del contenedor (Anexo B) o con un comando de una sola
        vez ejecutado localmente apuntando a la base de Neon.
     5) Como TRUST_PROXIES: en Render el trafico entra por su proxy interno y la
        IP del cliente llega en X-Forwarded-For. El origin no es alcanzable
        directamente desde Internet, asi que en ese caso concreto se puede usar
        TRUST_PROXIES=* (el .env.production.example lo prohibe pensando en un
        servidor con Nginx propio; aqui la justificacion es que nadie puede
        falsificar la cabecera porque nadie llega al contenedor sin pasar por
        Render). Documentar esta excepcion.
     6) Guardar los logs en la salida estandar (LOG_STACK=stderr) porque el
        disco es efimero y ademas es lo unico que se puede leer en el panel.

   Limitaciones que hay que aceptar:
     - Arranque en frio de ~1 minuto tras 15 de inactividad.
     - El respaldo diario NO puede correr (no hay cron ni disco): la proteccion
       queda a cargo de la ventana de restauracion de Neon. Alternativa
       gratuita: un flujo programado de GitHub Actions que ejecute pg_dump
       contra Neon y guarde el archivo como artefacto (Anexo E).
     - El log de auditoria (180 dias) se pierde en cada reinicio. Si se necesita
       auditoria persistente, esta opcion NO sirve.
     - Los Excel/PDF grandes pueden chocar con 512 MB de RAM.

 6.4 OPCION C - ALWAYSDATA (PLAN FREE)  (MEJOR OPCION SIN TARJETA)

   Verificado el 15/10/2026 en la documentacion oficial de alwaysdata. El plan
   gratuito incluye:

     Disco ............... 1 GB (incluye archivos, correo y bases de datos)
     RAM ................. 256 MB
     CPU ................. 1/4
     Respaldos ........... 3 dias moviles (administrados por el proveedor)
     Lenguajes ........... PHP (varias versiones, incluida 8.4) y otros
     Bases de datos ...... PostgreSQL y MySQL
     Tareas programadas .. SI (cron)
     HTTPS ............... SI, certificado gratuito incluido
     Precio .............. 0 (euros)

   Condiciones que hay que leer antes de decidir (estan en la letra chica):
     - "El plan Free no puede usarse con fines de lucro."
     - "La creacion de sitios en este plan esta limitada a la direccion de la
       cuenta alwaysdata.net" (es decir: NO se puede usar un dominio propio) y
       no permite ejecutar "services" (procesos propios de larga duracion).
       Para este sistema no es un problema: no hay workers ni demonios; la cola
       no se usa y el programador va por cron.
     - El uso institucional de una entidad estatal con un sistema sin fines de
       lucro encaja en la letra de la condicion, pero conviene confirmarlo con
       el proveedor antes de publicarlo.

   Por que encaja bien: es el unico proveedor SIN TARJETA que ofrece
   PHP + PostgreSQL + cron + HTTPS en un mismo lugar. Y el disco alcanza
   comodamente: vendor de produccion ~70 MB + codigo + dist 0,5 MB + base
   pequena, sobre 1 GB.

   Montaje resumido:
     1) Crear la cuenta y, en el panel, crear la base PostgreSQL (anotar host,
        puerto, base, usuario y contrasena).
     2) Subir el backend por SFTP/SSH a ~/api (o por git). Ejecutar
        `composer install --no-dev --optimize-autoloader` (Composer esta
        disponible por SSH) y completar el .env.
     3) Servir la API: en "Web > Sites" crear un sitio de tipo PHP apuntando al
        directorio public/ de Laravel. Los archivos estaticos de la SPA se
        colocan en la misma raiz que sirve el sitio, o se usa su funcion de
        "Rewrite rules" para enviar /api y /sanctum al index.php de Laravel y el
        resto a index.html. Esta es la parte que exige mas cuidado y pruebas.
     4) Migraciones y datos base desde SSH (seccion 5).
     5) Tarea programada: en "Advanced > Scheduled tasks", ejecutar cada minuto
        `php ~/api/artisan schedule:run`.
     6) Ajustar el memory_limit de PHP: con 256 MB de RAM conviene dejarlo en
        256M y evitar exportaciones enormes.

   Contras: 256 MB de RAM (justo para PHP-FPM + exportaciones), sin dominio
   propio, sin fines de lucro, y un panel poco comun si nunca se uso.

 6.5 OPCION D - SPA EN CDN + API EN OTRO HOST  (NO RECOMENDADA)

   Ejemplo: SPA en Cloudflare Pages o Netlify (ambos gratuitos) y API en un
   contenedor aparte.

   Por que NO: la sesion es una cookie (seccion 3.2). Habria que:
     - cambiar SESSION_SAME_SITE a none y SESSION_DOMAIN al dominio de la API;
     - activar SESSION_SECURE_COOKIE (ya lo esta);
     - declarar el dominio de la SPA en SANCTUM_STATEFUL_DOMAINS y en CORS;
     - Y AUN ASI, el navegador puede bloquear la cookie por ser de terceros.
   Ademas habria que reescribir el frontend para que llame a una URL absoluta.

   Si de todos modos se quisiera hacer, el unico camino serio es que el CDN
   ACTUE DE PROXY del mismo origen: en Cloudflare Pages se puede reenviar
   /api/* y /sanctum/* al backend con reglas de _redirects (rewrite 200 a una
   URL absoluta) o con una Function. Asi el navegador ve un solo dominio. Es
   mas fragil y agrega dependencia de la plataforma; solo tiene sentido si se
   necesita CDN global y no hay forma de tener un contenedor.

 6.6 OPCIONES DESCARTADAS (y por que)

   - InfinityFree, 000webhost, freehosting y similares: PHP con MySQL, sin
     PostgreSQL -> incumplen R2. Ademas sin SSH ni Composer, sin cron y con
     anuncios o limites de peticiones.
   - Heroku: elimino su capa gratuita.
   - Railway: ya no tiene plan gratuito (solo credito de prueba).
   - Fly.io: desde octubre de 2024 no hay capa gratuita para organizaciones
     nuevas (pago por uso; requiere tarjeta).
   - Vercel / Netlify / GitHub Pages / Cloudflare Pages por si solos: solo
     sirven estaticos -> incumplen R1 (no ejecutan Laravel).
   - Runtime PHP serverless de comunidad en Vercel: tecnicamente posible, pero
     sin sesiones fiables, sin cron, con arranques en frio y con un sistema de
     archivos de solo lectura -> incumple R3 en la practica.
   - Wasmer (Laravel gratis): MySQL -> incumple R2.
   - Koyeb: tiene instancia gratuita (1 servicio web de 512 MB / 2 GB de disco)
     y una base PostgreSQL gratuita, PERO la base gratuita esta limitada a
     5 horas de actividad y 1 GB, y la cuenta exige tarjeta (con cargo del plan
     prorrateado al registrarse, que luego se puede bajar al plan Starter).
     Como base de datos persistente no sirve; como servicio web es equivalente

================================================================================
 7. AJUSTES OBLIGATORIOS POR LAS LIMITACIONES DEL PLAN GRATUITO
================================================================================

 7.1 COLA: QUEUE_CONNECTION -> sync
   El sistema no encola nada (no hay Jobs/ShouldQueue). En un plan gratuito no
   hay worker ni cron por minuto para el worker, asi que:
       QUEUE_CONNECTION=sync
   Con database tambien funciona (nada se encola), pero sync evita dejar filas
   huerfanas si en el futuro alguien agrega un Job sin worker.

 7.2 LOGS: A DONDE ESCRIBIR
   - En un servidor propio o con disco (Opcion A/C): dejar `daily` (30 dias) y
     el canal `auditoria` (180 dias) tal como viene. Es la configuracion legal
     correcta.
   - En un PaaS con disco efimero (Opcion B): poner
       LOG_CHANNEL=stderr
     para que los logs salgan al panel del proveedor y no se pierdan en el
     disco. OJO: el canal `auditoria` sigue escribiendo a archivo, asi que en un
     PaaS efimero LA AUDITORIA SE PIERDE. Si la auditoria hace falta, la Opcion
     B queda descartada.

 7.3 RESPALDOS
   - Con cron y pg_dump (Opcion A): dejar el programador como esta
     (`sinchiwayra:respaldar` a las 02:30) y apuntar RESPALDO_DIRECTORIO a un
     disco/volumen fuera del arbol de la aplicacion, por ejemplo
     /var/backups/sinchiwayra. Ademas, copiar ese directorio periodicamente
     fuera del servidor (otro disco, rclone, o descarga manual): un respaldo en
     el mismo servidor no protege de perder el servidor.
   - Sin cron (Opcion B): usar la restauracion a un punto en el tiempo del
     proveedor de base de datos (Neon) y/o un flujo programado de GitHub
     Actions que ejecute pg_dump contra la base y guarde el artefacto
     (plantilla en el Anexo E).
   - Sin pg_dump (algunos hostings no lo tienen): revisar `PG_DUMP_PATH`; si no
     existe el binario, el respaldo programado falla (y avisa por el canal de
     auditoria con estado "fallido"). En ese caso, respaldar desde otra maquina.

 7.4 SESIONES Y CACHE
   Ya estan en la base de datos (SESSION_DRIVER=database, CACHE_STORE=database).
   No cambiar a `file` en un PaaS efimero: se perderia la sesion en cada
   reinicio y los usuarios serian expulsados.

 7.5 HTTPS Y PROXY TLS
   En todos los casos el sitio debe servirse SOLO por HTTPS porque
   SESSION_SECURE_COOKIE=true y SESSION_ENCRYPT=true. Si el TLS lo termina un
   proxy (un CDN, o el balanceador del PaaS) y la aplicacion ve HTTP, hay que
   indicarle que confie en el proxy: TRUST_PROXIES (ver 7.6) y, en Nginx,
   pasar HTTPS/HTTP_X_FORWARDED_PROTO al FastCGI (Anexo C).

 7.6 TRUST_PROXIES (IP del cliente)
   - Nginx en el mismo servidor, sin nada delante: dejar TRUST_PROXIES vacio.
     FastCGI ya le pasa a PHP la IP real del cliente.
   - Con Cloudflare u otro proxy delante: poner SOLO las redes de ese proxy,
     nunca '*'. Excepcion justificada: en un PaaS donde el contenedor no es
     alcanzable desde Internet (Render), usar '*' es aceptable porque nadie
     puede falsificar X-Forwarded-For sin pasar por el proveedor. Dejar
     constancia de la decision.
   - Sintoma de tenerlo mal: en el log de auditoria todas las IP son la del
     proxy, o (peor) un cliente puede falsear su IP.

 7.7 MEMORIA
   - 512 MB (Render) o 256 MB (Alwaysdata): fijar memory_limit de PHP en 256M y
     evitar exportar reportes de rangos enormes. Las exportaciones a Excel son
     las que mas memoria consumen.

 7.8 DOMINIO GRATUITO
   - Sin dominio propio (Alwaysdata): la URL sera algo como
     https://cuenta.alwaysdata.net. Funciona, pero no es institucional y ata la
     direccion al proveedor.
   - Con subdominio de prueba: servicios como nip.io/sslip.io permiten probar
     HTTPS con un nombre tipo 203-0-113-5.nip.io sin comprar dominio. Solo para
     pruebas, no para entrega.

 10. CI/CD GRATUITO CON GITHUB ACTIONS
================================================================================

 El repositorio ya esta en GitHub: https://github.com/MCarranzas/epcoro
 (rama main). GitHub Actions es gratuito para repositorios publicos y trae
 minutos incluidos para privados.

 10.1 QUE CONVIENE AUTOMATIZAR

   - Pruebas del backend (PHPUnit) con un servicio PostgreSQL.
   - Analisis estatico (PHPStan/Larastan) y formato (Pint --test).
   - Chequeo de tipos y build del frontend (vue-tsc + vite build).
   - Despliegue (solo si el proveedor tiene "deploy hook" o si se despliega por
     SSH a la VM de la Opcion A).

 10.2 PLANTILLA DE FLUJO (guardar como .github/workflows/ci.yml)

   ---------------------------------------------------------------------------
   name: CI

   on:
     push:
       branches: [main]
     pull_request:

   jobs:
     api:
       runs-on: ubuntu-latest

       services:
         postgres:
           image: postgres:17
           env:
             # El phpunit.xml del proyecto fija estas credenciales; el servicio
             # de CI debe crearlas tal cual.
             POSTGRES_USER: epcoro
             POSTGRES_PASSWORD: epcoro_secret
             POSTGRES_DB: epcoro_test
           ports:
             - 5432:5432
           options: >-
             --health-cmd "pg_isready -U epcoro"
             --health-interval 10s
             --health-timeout 5s
             --health-retries 5

       defaults:
         run:
           working-directory: epcoro-api

       steps:
         - uses: actions/checkout@v4

         - uses: shivammathur/setup-php@v2
           with:
             php-version: '8.4'
             extensions: bcmath, pdo_pgsql, pgsql, mbstring, gd, zip, intl, curl
             coverage: none

         - run: composer install --no-interaction --prefer-dist

         - run: cp .env.example .env && php artisan key:generate

         - run: php artisan test

         - run: vendor/bin/phpstan analyse --no-progress
         - run: vendor/bin/pint --test

     web:
       runs-on: ubuntu-latest

       defaults:
         run:
           working-directory: epcoro-web

       steps:
         - uses: actions/checkout@v4
         - uses: actions/setup-node@v4
           with:
             node-version: '24'
             cache: npm
             cache-dependency-path: epcoro-web/package-lock.json

         - run: npm ci
         - run: npm run build

   Notas:

================================================================================
 13. LIMITES, RIESGOS Y QUE NO HACER CON UN PLAN GRATUITO
================================================================================

   Riesgos por opcion:

     A) VM always-free
        - Riesgo de operacion: nadie parchea el servidor si no hay alguien
          asignado. Requiere tarjeta (aunque no cobre si se respetan los cupos).
        - El proveedor puede reclamar la VM si esta inactiva durante mucho
          tiempo; y los cupos gratuitos cambian (Oracle ya redujo Ampere en 2026).

     B) Render + Neon
        - Arranque en frio de ~1 min tras 15 min sin trafico.
        - Disco efimero: se pierde la auditoria de 180 dias y los respaldos.
        - La base gratuita de Render expira a los 30 dias: por eso se usa Neon.
        - Render dice explicitamente que su plan gratuito no es para produccion.
        - 750 h/mes: un solo servicio 24/7 consume casi todo el cupo.
        - Hay que avivar el servicio para demostraciones (o aceptar el minuto
          de espera delante del cliente).

     C) Alwaysdata
        - 256 MB de RAM: justo para exportaciones grandes.
        - Sin dominio propio y con la clausula de "sin fines de lucro".
        - Al ser un hosting compartido, no se controla el resto del servidor.

   Que NO hacer:
     - NO usar el plan gratuito como entorno definitivo de datos fiscales sin
       respaldo externo y sin auditoria persistente.
     - NO usar MySQL ni SQLite "para simplificar": las migraciones son de
       PostgreSQL y fallan.
     - NO correr `php artisan migrate:fresh` ni `db:seed` a secas en produccion:
       borran y crean cuentas de demostracion.
     - NO dejar APP_DEBUG=true para "ver mejor los errores": expone trazas,
       rutas y credenciales.
     - NO versionar el .env ni subir usuarios_prueba.txt al servidor.
     - NO confiar en un respaldo guardado en el mismo servidor.
     - NO ejecutar el .exe ni los comandos de desarrollo en el servidor.

 # syntax=docker/dockerfile:1
 #
 # SINCHI WAYRA - imagen UNICA que sirve la SPA (Vue) y la API (Laravel) en el
 # MISMO origen. Es un requisito del sistema: la autenticacion es por cookie de
 # sesion (Sanctum modo SPA) y el cliente axios usa la ruta relativa /api/v1, asi
 # que la SPA y la API no pueden vivir en dominios distintos.
 #
 # El contexto de build debe ser la RAIZ del repositorio (epcoro/), porque se
 # copian tanto epcoro-web/ como epcoro-api/.
 #
 #   Etapa 1 (web)   : Node 24 compila la SPA  ->  /web/dist
 #   Etapa 2 (final) : PHP 8.4 + Nginx sirve la SPA y enruta /api y /sanctum a
 #                     PHP-FPM, todo en el mismo puerto (el que inyecta $PORT).

 # ---------------------------------------------------------------------------
 # Etapa 1: construir la SPA (vue-tsc -b && vite build)
 # ---------------------------------------------------------------------------
 FROM node:24-alpine AS web

 WORKDIR /web
 COPY epcoro-web/package.json epcoro-web/package-lock.json ./
 RUN npm ci
 COPY epcoro-web/ ./
 RUN npm run build

 # ---------------------------------------------------------------------------
 # Etapa 2: PHP 8.4 + PostgreSQL + Nginx
 # ---------------------------------------------------------------------------
 FROM php:8.4-fpm-alpine

 # nginx          -> servidor web (sirve la SPA y pasa /api y /sanctum a PHP)
 # gettext        -> envsubst (inyecta el puerto $PORT en la plantilla de nginx)
 # postgresql-dev -> cabeceras para compilar pdo_pgsql / pgsql
 # libzip/libpng/libjpeg/freetype/icu/oniguruma -> zip, gd, intl, mbstring
 RUN apk add --no-cache \
         nginx \
         gettext \
         postgresql-dev \
         libzip-dev \
         libpng-dev \
         libjpeg-turbo-dev \
         freetype-dev \
         icu-dev \
         oniguruma-dev \
     && docker-php-ext-configure gd --with-freetype --with-jpeg \
     && docker-php-ext-install -j"$(nproc)" \
         pdo_pgsql pgsql bcmath gd zip intl mbstring opcache \
     && rm -rf /var/cache/apk/*

 # PHP-FPM: escuchar solo en loopback y HEREDAR el entorno del contenedor.
 # clear_env=no es imprescindible: en un PaaS las variables (APP_KEY, DB_*,
 # SANCTUM_*) llegan como variables de entorno del contenedor, no como
 # archivo .env, y por defecto PHP-FPM las borraria.
 RUN sed -i 's/^listen = .*/listen = 127.0.0.1:9000/' /usr/local/etc/php-fpm.d/www.conf \

 --- docker/start.sh ---
 ------------------------------------------------------------------------------
 #!/bin/sh
 # SINCHI WAYRA - arranque del contenedor.
 #
 # Deja todo listo y levanta PHP-FPM + Nginx en el puerto que inyecta el
 # proveedor ($PORT). Se ejecuta en CADA arranque del contenedor: cachea la
 # configuracion con las variables ya inyectadas, aplica migraciones y arranca.
 set -e

 cd /var/www/api

 echo "[start] Generando la configuracion de Nginx para el puerto ${PORT:-8080}"
 envsubst '${PORT}' < /etc/nginx/http.d/default.conf.template > /etc/nginx/http.d/default.conf

 echo "[start] Cacheando configuracion, rutas y vistas"
 # config:cache DEBE correr aqui (y no en el build): lee las variables de
 # entorno que el proveedor inyecta en tiempo de ejecucion. Es critico: si
 # falla, se detiene el arranque.
 php artisan config:cache
 # Rutas y vistas: si no se pueden cachear (por ejemplo una ruta con closure),
 # se avisa y se sigue con el arranque normal en vez de bloquear el servicio.
 php artisan route:cache || echo "[start] AVISO: no se pudo cachear rutas; se usaran dinamicas."
 php artisan view:cache || echo "[start] AVISO: no se pudieron cachear vistas."

 echo "[start] Aplicando migraciones (con reintentos por si la base aun arranca)"
 intentos=0
 until php artisan migrate --force; do
     intentos=$((intentos + 1))
     if [ "$intentos" -ge 30 ]; then
         echo "[start] ERROR: la base de datos no respondio tras $intentos intentos." >&2
         exit 1
     fi
     echo "[start] Esperando a la base de datos... (intento $intentos)"
     sleep 3
 done

 # Seeders de datos base: se corren UNA SOLA VEZ. Definir SEED=1 en las variables
 # del servicio, desplegar, y luego QUITAR la variable para no repetirlos en cada
 # reinicio. Ver el Anexo F.
 if [ "${SEED:-0}" = "1" ]; then
     echo "[start] Sembrando datos base (SEED=1)"
     php artisan db:seed --class=RolPermisosSeeder       --force
     php artisan db:seed --class=CatalogoGeograficoSeeder --force
     php artisan db:seed --class=PresentacionesSeeder    --force
     php artisan db:seed --class=ParametrosSeeder        --force
     php artisan db:seed --class=CompradoresSeeder       --force
     php artisan db:seed --class=AdminSeeder             --force
 fi

 # Lo que Laravel escribe en disco debe ser del usuario de PHP-FPM (www-data).
 chown -R www-data:www-data storage bootstrap/cache || true

 echo "[start] Arrancando PHP-FPM y Nginx"
 php-fpm -D
 exec nginx -g 'daemon off;'

 ANEXO C - NGINX (un solo dominio: SPA + API)
================================================================================

 Archivo REAL: `docker/nginx.conf.template`. Se llama .template a proposito:
 Nginx no debe cargarlo tal cual porque contiene el literal ${PORT}.
 `docker/start.sh` lo reemplaza con envsubst y lo escribe como
 /etc/nginx/http.d/default.conf.

 ------------------------------------------------------------------------------
 server {
     listen ${PORT};
     server_name _;

     root /var/www/web;                 # dist/ compilado de la SPA
     index index.html;

     client_max_body_size 12m;

     # --- API, CSRF de Sanctum y health check -> Laravel (PHP-FPM) ---
     location ~ ^/(api|sanctum|up)(/|$) {
         include fastcgi_params;
         fastcgi_pass 127.0.0.1:9000;

         fastcgi_param SCRIPT_FILENAME /var/www/api/public/index.php;
         fastcgi_param SCRIPT_NAME     /index.php;
         fastcgi_param DOCUMENT_ROOT   /var/www/api/public;
         fastcgi_param REQUEST_URI     $request_uri;
         fastcgi_param HTTPS           $https if_not_empty;

         # El proxy TLS del proveedor termina el HTTPS y manda la cabecera.
         # Reenviarla es lo que hace que Laravel ($request->isSecure()) genere
         # URLs https y acepte la cookie SESSION_SECURE_COOKIE=true.
         fastcgi_param HTTP_X_FORWARDED_PROTO $http_x_forwarded_proto;
         fastcgi_param HTTP_X_FORWARDED_FOR   $http_x_forwarded_for;
         fastcgi_param HTTP_X_FORWARDED_HOST  $http_x_forwarded_host;

         fastcgi_read_timeout 120s;
     }

     # --- Estaticos con hash en el nombre: cache agresiva ---
     location /assets/ {
         expires 30d;
         add_header Cache-Control "public, immutable";
         try_files $uri =404;
     }

     # --- SPA con historial HTML5: todo lo demas cae en index.html ---
     location / {
         try_files $uri /index.html;
     }
 }
 ------------------------------------------------------------------------------

 En un PaaS (Railway, Render), ${PORT} lo inyecta el proveedor y start.sh hace
 el envsubst. En un servidor propio, reemplazar `listen ${PORT};` por
 `listen 443 ssl;` con el certificado, mas un `server` en el 80 que redirija
 a https.

 on:

   dump:
     runs-on: ubuntu-latest
     steps:

           sudo sh -c 'echo "deb https://apt.postgresql.org/pub/repos/apt $(lsb_release -cs)-pgdg main" > /etc/apt/sources.list.d/pgdg.list'
           curl -fsSL https://www.postgresql.org/media/keys/ACCC4CF8.asc | sudo gpg --dearmor -o /etc/apt/trusted.gpg.d/pgdg.gpg

           PGPASSWORD: ${{ secrets.DB_PASSWORD }}
         run: |
           pg_dump --host=${{ secrets.DB_HOST }} --port=5432 \
             --username=${{ secrets.DB_USERNAME }} --format=custom \
             --no-password --file=sinchiwayra-$(date +%Y-%m-%d_%H%M%S).dump \
             ${{ secrets.DB_DATABASE }}

       - name: Guardar el respaldo como artefacto
         uses: actions/upload-artifact@v4
         with:
           name: respaldo
           path: sinchiwayra-*.dump
           retention-days: 30
 ------------------------------------------------------------------------------

 Notas: los artefactos de Actions tienen retencion limitada y no son un archivo
 fiscal; para respaldos serios, subirlos a un almacenamiento de objetos con
 cifrado. Los secretos (DB_HOST, DB_USERNAME, DB_PASSWORD, DB_DATABASE) van en
 Settings > Secrets and variables > Actions.

================================================================================
 ANEXO F - SEEDERS: QUE CORRER EN PRODUCCION (IMPORTANTE)
================================================================================

 `php artisan db:seed` (sin argumentos) ejecuta DatabaseSeeder, que llama a
 TODOS los seeders, incluidos los de demostracion. En produccion eso crea las
 cuentas de ejemplo. NO HACER ESO.

 Lo que hay que correr en produccion, en este orden:

   php artisan db:seed --class=RolPermisosSeeder       --force
   php artisan db:seed --class=CatalogoGeograficoSeeder --force
   php artisan db:seed --class=PresentacionesSeeder    --force
   php artisan db:seed --class=ParametrosSeeder        --force
   php artisan db:seed --class=CompradoresSeeder       --force
   php artisan db:seed --class=AdminSeeder             --force

 Comportamiento en produccion de cada seeder:
   - RolPermisosSeeder ......... roles y permisos. IMPRESCINDIBLE.
   - CatalogoGeograficoSeeder .. departamentos/provincias/municipios. Necesario.
   - PresentacionesSeeder ...... catalogo de presentaciones del mineral.
   - ParametrosSeeder .......... parametros del formulario (aporte, regalias,
                                 cotizacion base...). Necesario para calcular.
   - CompradoresSeeder ......... comprador institucional fijo.
   - AdminSeeder ............... crea el usuario administrador. En produccion
                                 (APP_ENV=production) genera una contrasena
                                 ALEATORIA de 24 caracteres y la muestra UNA
                                 SOLA VEZ por consola, con cambio obligatorio en
                                 el primer ingreso. Anotarla en ese momento.

 Seeders que NO deben correr en produccion:

   - VendedoresEjemploSeeder, CompradoresEjemploSeeder,
     AreasMinerasEjemploSeeder  -> datos de demostracion. Tienen una guarda que
     los omite solos cuando APP_ENV=production, pero no hay que invocarlos.
   - UsuariosEjemploSeeder  -> ATENCION: NO tiene guarda de produccion. Si se
     ejecuta en produccion CREA las cuentas tecnico, tecnico2, revisor y
     gerente con contrasenas aleatorias. El propio comentario del archivo dice
     "en produccion ninguna de estas cuentas debe existir". NO EJECUTARLO.

   Como verificar despues de sembrar:
     php artisan tinker
     >>> App\Models\User::pluck('username');
     # Solo deben aparecer las cuentas reales (por ejemplo: admin) y ninguna
     # cuenta de demostracion (tecnico, tecnico2, revisor, gerente).

 Las contrasenas de desarrollo de esas cuentas estan en usuarios_prueba.txt.
 Ese archivo es material de desarrollo: NUNCA debe subirse al servidor.

 ANEXO G - RAILWAY (imagen unica: SPA + API en el mismo origen)
================================================================================

 AVISO SOBRE EL COSTO: Railway YA NO tiene plan gratuito. Las cuentas nuevas
 reciben un credito de prueba (del orden de USD 5 por 30 dias) y despues un
 credito mensual minimo; agotado ese credito, los servicios se detienen. Para
 "gratis de verdad" usar la Opcion B (Render + Neon) o la Opcion C (Alwaysdata).

 Lo que sigue aplica igual a las tres opciones: es la MISMA imagen (Anexo B),
 un solo servicio que sirve SPA y API en el mismo origen.

 Guia paso a paso, tabla completa de variables y errores frecuentes:
   deploy_railway/despliegue_railway.md

 Resumen:
   1) Railway: New Project > Deploy from GitHub repo (MCarranzas/epcoro). Dejar
      el "Root Directory" en la RAIZ del repositorio (NO en epcoro-api).
      Railway usa railway.toml y el Dockerfile para construir.
   2) + New > Database > PostgreSQL (dejandola PRIVADA). Railway expone PGHOST,
      PGPORT, PGUSER, PGPASSWORD y PGDATABASE.
   3) Variables del servicio: las de la seccion 4, con DB_* referenciando el
      servicio Postgres:
        DB_HOST=${{Postgres.PGHOST}}        DB_PORT=${{Postgres.PGPORT}}
        DB_DATABASE=${{Postgres.PGDATABASE}}
        DB_USERNAME=${{Postgres.PGUSER}}    DB_PASSWORD=${{Postgres.PGPASSWORD}}
      Mas: TRUST_PROXIES=* (excepcion justificada, ver 7.6), QUEUE_CONNECTION=sync
      y LOG_STACK=stderr (disco efimero).
   4) Settings > Networking > Generate Domain. Con esa URL fijar APP_URL,
      CORS_ALLOWED_ORIGINS, FRONTEND_URL y SANCTUM_STATEFUL_DOMAINS (este SIN
      https:// y SIN puerto). Redeploy.
   5) Primer arranque: start.sh corre migraciones solo. Para sembrar los datos
      base (Anexo F), definir SEED=1 una vez, copiar la contrasena del admin
      desde los logs del deploy y QUITAR SEED.

 Comprobacion: GET /up -> 200; GET /api/health -> JSON con la base de datos;
 y un login real que sostenga la sesion.
