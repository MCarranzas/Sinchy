GUÍA DE PUESTA EN PRODUCCIÓN EN RAILWAY Laravel 13.34.0 + PHP 8.4 +
PostgreSQL 17 + Vue 3.5 + Vite 8 + TypeScript + Tailwind CSS 4 Objetivo:
publicar el sistema desde GitHub durante una prueba de una semana,
intentando no pagar.

IMPORTANTE: COSTO Y LÍMITES - Railway ofrece a las cuentas nuevas una
prueba con un crédito único de USD 5, válido durante 30 días. No es una
promesa de que cualquier aplicación funcione una semana sin consumir
todo el crédito. - Después de la prueba, el plan Free ofrece USD 1 de
crédito mensual. El consumo depende del tiempo activo, CPU, RAM,
almacenamiento y red. - Para intentar mantener el costo en USD 0: no
cambies al plan Hobby ni a otro plan de pago, no agregues servicios
innecesarios y no ingreses/confirmes una mejora de plan. Con el crédito
agotado, los servicios pueden detenerse. - Antes de desplegar, revisa en
Railway el plan activo, los créditos y la sección Usage. La interfaz y
las condiciones pueden cambiar. - Una base de datos de prueba puede
perderse o dejar de estar disponible al terminar la prueba. Exporta los
datos que necesites antes de finalizar. - No uses datos personales o
productivos reales durante esta prueba.

PARTE 1. PREPARAR EL REPOSITORIO GITHUB

1.  Comprueba cómo está organizado el código:
    A)  Si el repositorio contiene Laravel y, dentro del mismo proyecto,
        package.json, vite.config.ts y la carpeta resources/js (o
        equivalente), probablemente sea un proyecto Laravel con Vue
        integrado.
    B)  Si Laravel y Vue están en carpetas/repositorios independientes,
        tendrás que crear un servicio Railway para Laravel y otro para
        el frontend Vue. Esta guía explica ambas opciones.
2.  Comprueba en tu proyecto Laravel:
    -   Debe existir composer.json.
    -   Debe existir un archivo .env.example.
    -   .env NO debe estar publicado en GitHub.
    -   APP_KEY, contraseñas, claves API y credenciales no deben estar
        en el repositorio.
    -   Debe estar disponible la configuración PostgreSQL en
        config/database.php.
    -   Si usas autenticación, almacenamiento de archivos, correo, colas
        o tareas programadas, revisa sus variables y dependencias antes
        de la prueba.
3.  No es obligatorio crear un Dockerfile para empezar. Railway
    documenta el despliegue de Laravel desde GitHub y puede detectar una
    aplicación Laravel y ejecutarla con PHP-FPM y Caddy. Si la detección
    falla o necesitas extensiones/versiones específicas, revisa los logs
    y la guía oficial; podría ser necesario añadir configuración
    adicional.

PARTE 2. CREAR LA CUENTA Y EL PROYECTO RAILWAY

1.  Abre https://railway.com/ y selecciona Login/Sign up.
2.  Vincula tu cuenta de GitHub cuando Railway lo solicite. Esto también
    puede ser necesario para verificar el acceso de red de la prueba.
3.  Revisa el plan mostrado. Confirma que estás en Trial/Free y que no
    has seleccionado Hobby.
4.  Crea un proyecto nuevo y elige Deploy from GitHub repo.
5.  Autoriza a Railway para acceder al repositorio que contiene Laravel
    y selecciónalo.
6.  Si el panel ofrece Deploy Now, puedes iniciar el despliegue, pero es
    preferible revisar y completar las variables antes de considerar el
    servicio listo.
7.  Si tienes Laravel y Vue en repositorios separados, despliega primero
    Laravel siguiendo los pasos siguientes. Después crea otro servicio
    desde el repositorio Vue.

PARTE 3. CREAR POSTGRESQL

1.  En el canvas del proyecto Railway, pulsa + New (o el botón
    equivalente) y elige Database > PostgreSQL.
2.  Espera a que se cree el servicio. Railway expone variables como
    PGHOST, PGPORT, PGUSER, PGPASSWORD, PGDATABASE y DATABASE_URL.
3.  Comprueba la versión real del servidor. No asumas que será
    PostgreSQL 17 solo por la versión de tu entorno local. Si la
    aplicación requiere específicamente PostgreSQL 17, verifica la
    versión del servicio y las opciones de imagen disponibles antes de
    migrar datos.
4.  Mantén la base de datos privada dentro del proyecto. No habilites
    acceso público/TCP proxy para esta prueba: no es necesario para que
    Laravel se conecte desde el mismo proyecto y puede generar consumo
    adicional.
5.  No cargues datos reales. Si tienes datos locales que necesitas
    probar, usa una copia de prueba sin información sensible.

PARTE 4. CONFIGURAR VARIABLES DEL SERVICIO LARAVEL

1.  Abre el servicio Laravel en Railway y entra en Variables.

2.  Añade las variables básicas siguientes. Sustituye los valores de
    ejemplo por los reales:

    APP_NAME=MiSistema APP_ENV=production APP_DEBUG=false
    APP_KEY=base64:VALOR_GENERADO
    APP_URL=https://TU-DOMINIO.up.railway.app LOG_CHANNEL=stderr
    DB_CONNECTION=pgsql
    DB_HOST=Postgres.PGHOSTDB_(P)ORT={{Postgres.PGPORT}}
    DB_DATABASE=Postgres.PGDATABASEDB_(U)SERNAME={{Postgres.PGUSER}}
    DB_PASSWORD=${{Postgres.PGPASSWORD}}

    NOTA: “Postgres” debe coincidir exactamente con el nombre del
    servicio de base de datos en tu proyecto. Si le pusiste otro nombre,
    cambia el prefijo de las referencias. Railway permite referencias
    entre variables de servicios con la sintaxis
    ${{NombreServicio.VARIABLE}}.

3.  Genera APP_KEY de forma segura. En tu copia local del proyecto
    Laravel, abre una terminal en la carpeta que contiene artisan y
    ejecuta: php artisan key:generate –show Copia el valor completo que
    imprime y pégalo como APP_KEY en Railway. No publiques esta clave ni
    la compartas. No generes una clave nueva cada vez que despliegues,
    porque puede invalidar sesiones o datos cifrados existentes.

4.  Si no tienes PHP instalado localmente, puedes generar una clave con
    un entorno PHP confiable o preparar el proyecto primero en tu
    equipo. No inventes una clave manualmente.

5.  Añade también las variables que requiera tu aplicación:

    -   SESSION_DRIVER: conserva el valor compatible con tu
        configuración. Si usas sesiones en base de datos, asegúrate de
        que existan las migraciones/tablas necesarias.
    -   CACHE_STORE o CACHE_DRIVER: usa el nombre esperado por tu
        versión/configuración de Laravel.
    -   QUEUE_CONNECTION: si no utilizas trabajos en segundo plano, no
        agregues un worker innecesario; conserva una configuración
        sencilla compatible con el proyecto.
    -   MAIL_*: solo si vas a probar correo.
    -   Variables de servicios externos: solo si realmente se usan. No
        copies el archivo .env completo sin revisarlo y nunca pegues
        APP_DEBUG=true en producción.

6.  Guarda las variables y revisa si Railway pide desplegar de nuevo
    para aplicarlas.

PARTE 5. COMPILAR VUE/VITE

CASO A: VUE ESTÁ INTEGRADO EN LARAVEL 1. Comprueba que package.json
define un script build (habitualmente “build”: “vite build”) y que
existe vite.config.ts. 2. La guía de Railway para Laravel contempla
añadir npm run build como Custom Build Command cuando corresponda. Si la
detección automática ya ejecuta la compilación, evita duplicarla. 3. Si
el despliegue falla por dependencias o por Node, consulta los build
logs. Asegúrate de que el repositorio incluya package-lock.json (si usas
npm) y que las versiones de Node y dependencias sean compatibles. 4.
Revisa la configuración de Vite. Si el frontend se sirve desde Laravel,
no configures una URL de API independiente sin necesidad. 5. Si el
proyecto usa variables VITE_, recuerda que normalmente se incorporan al
bundle durante la compilación y son visibles en el navegador. Nunca
pongas secretos en variables VITE_.

CASO B: VUE ESTÁ EN UN REPOSITORIO/CARPETA SEPARADO 1. En Railway crea
otro servicio desde el repositorio del frontend. 2. Configura el
directorio raíz del servicio si el frontend está en una subcarpeta. 3.
Configura el comando de build npm run build. 4. El directorio de salida
de Vite suele ser dist. Configura un servicio de sitio estático si está
disponible para tu proyecto, o el mecanismo de publicación de archivos
estáticos recomendado por Railway. 5. Define la variable pública que tu
código use para llamar a la API, por ejemplo
VITE_API_URL=https://TU-API.up.railway.app. Usa el nombre exacto que
espera tu aplicación. Las variables VITE_* no son secretas. 6. En
Laravel configura CORS para aceptar únicamente el origen del frontend de
Railway. Comprueba también las cookies/sesiones y CSRF si utilizas
autenticación basada en cookies. 7. En el frontend, no uses localhost
como URL de API en producción.

PARTE 6. DOMINIO PÚBLICO

1.  En el servicio Laravel, abre Settings > Networking (el nombre puede
    variar) y selecciona Generate Domain.
2.  Copia la URL HTTPS que Railway genere.
3.  Actualiza APP_URL con esa URL, sin añadir una barra final si tu
    configuración no la requiere.
4.  Si Vue está separado, configura VITE_API_URL con la URL pública de
    Laravel, vuelve a desplegar el frontend y configura CORS en Laravel.
5.  No compartas el dominio hasta comprobar que APP_DEBUG=false y que
    las rutas sensibles están protegidas.

PARTE 7. MIGRACIONES DE BASE DE DATOS

Antes de ejecutar migraciones, confirma que la base está vacía o que
tienes una copia de seguridad. migrate:fresh elimina tablas y datos: NO
lo ejecutes en una base que quieras conservar.

Opción recomendada para un despliegue de prueba: 1. Abre Settings/Deploy
del servicio Laravel. 2. Si la plataforma permite Pre-Deploy Command,
configura: php artisan migrate –force 3. Si no tienes esa opción,
utiliza la consola/terminal del servicio si está disponible o el método
recomendado por la guía vigente de Railway para ejecutar el comando una
sola vez. 4. No ejecutes migraciones repetidamente de forma manual sin
revisar su estado. 5. Si tienes seeders, ejecútalos solo si sabes
exactamente qué datos crean. No ejecutes seeders con contraseñas
predeterminadas en un sitio público.

Si aparecen errores de conexión: - Comprueba que DB_CONNECTION=pgsql. -
Comprueba que los nombres de variables y las referencias al servicio
PostgreSQL coinciden. - Comprueba que el servicio PostgreSQL está
activo. - Revisa los logs de despliegue y de la aplicación. - Comprueba
que las migraciones son compatibles con PostgreSQL; una aplicación
desarrollada solo para MySQL puede requerir ajustes.

PARTE 8. PRUEBAS FUNCIONALES

Prueba, en este orden: [ ] La URL pública responde por HTTPS. [ ] No
aparece la página de error de Laravel ni un error 500. [ ] Puedes
iniciar sesión y cerrar sesión. [ ] Las consultas leen y escriben en
PostgreSQL. [ ] Crear, editar y eliminar registros funciona según lo
esperado. [ ] Las validaciones del backend funcionan. [ ] Vue carga CSS,
JavaScript e imágenes sin errores 404. [ ] Las llamadas a la API
funcionan y no hay errores CORS. [ ] Las cargas de archivos, correos,
colas y tareas programadas se prueban solo si forman parte del sistema.
[ ] APP_DEBUG=false. [ ] No se exponen credenciales ni información
sensible en el navegador o los logs.

PARTE 9. CONTROLAR EL COSTO DURANTE LOS 7 DÍAS

1.  En Railway abre Workspace/Account Settings > Usage (o la sección de
    consumo equivalente).
2.  Revisa los créditos restantes y el uso estimado al menos al inicio y
    cada día de la prueba.
3.  Mantén solamente los servicios imprescindibles: Laravel, PostgreSQL
    y, si el frontend está separado, el frontend.
4.  Evita crear servicios redundantes, réplicas, workers, cron jobs o
    volúmenes que no necesites.
5.  No habilites acceso público a PostgreSQL.
6.  No actualices a Hobby ni añadas un método de pago para ampliar el
    uso si tu requisito es no pagar. Lee cuidadosamente cualquier
    pantalla de actualización.
7.  Si el consumo se acerca al crédito disponible, detén o elimina los
    servicios que no necesites desde el panel. Detener/eliminar
    servicios puede dejar la aplicación inaccesible; exporta antes los
    datos que necesites.
8.  El crédito de prueba es limitado y el costo real depende del uso. No
    es posible garantizar que siete días de actividad entren en USD 5
    sin conocer el consumo del sistema.
9.  Al terminar el séptimo día:
    -   Exporta la base de datos si necesitas conservarla.
    -   Descarga cualquier archivo subido que quieras guardar; el
        sistema de archivos efímero del servicio no es almacenamiento
        permanente.
    -   Elimina el proyecto/servicios si ya no los necesitas,
        verificando primero qué recursos y datos se borrarán.
    -   Comprueba la sección Usage y el plan activo.

PARTE 10. ERRORES FRECUENTES

-   Error de APP_KEY: define una clave válida y estable en Variables.
-   Error de conexión PostgreSQL: revisa DB_* y las referencias
    ${{Postgres.PGHOST}}, etc.
-   Error de build de Vite: revisa package.json, package-lock.json, Node
    y los logs de build.
-   Error 500: mira los logs de Railway; mantén APP_DEBUG=false
    públicamente.
-   Error CORS: agrega el origen exacto del frontend en la configuración
    CORS de Laravel.
-   Rutas SPA que devuelven 404: revisa el fallback de rutas del
    frontend y la configuración de hosting.
-   Archivos subidos desaparecen: el disco local del contenedor puede
    ser efímero. No dependas de él para conservar archivos; durante una
    prueba usa archivos ficticios o un almacenamiento
    persistente/externo compatible.
-   PostgreSQL no tiene la versión esperada: verifica la versión real
    del servidor antes de migrar datos.
